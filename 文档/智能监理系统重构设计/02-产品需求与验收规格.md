# 智能监理系统重构产品需求与验收规格

版本：0.1（评审稿）  
日期：2026-10-20  
状态：需求评审前草案；业务规则中标记“待确认”的项目不可被实现默认化

## 1. 产品目标

为监理人员提供统一的自然语言和多模态业务入口，支持从描述、照片、文档和历史业务数据中整理可追溯的现场事项，匹配适用表单和业务流程，生成可编辑草稿，并在权限和确认条件满足后执行记录、隐患、文书、台账和汇总操作。

系统应减少重复录入，但不得以自动化为理由把不确定推断写成现场事实。正确理解“不知道/缺失/冲突”是需求，不是失败。

## 2. 用户及权限

| 用户角色 | 主要职责 | 能力范围（具体权限按项目授权配置） |
|---|---|---|
| 监理员 | 现场巡视、影像采集、草稿整理 | 创建/补充授权范围内的现场记录和问题报告 |
| 专业监理工程师 | 专业检查、验收、旁站、记录审核 | 处理专业记录、审核或复查授权事项 |
| 总监/总监代表 | 项目管理、文书审签、日志/月报审核 | 执行授予的审批、签发和归档操作 |
| 项目管理员 | 项目基础信息、人员、表单配置 | 管理项目字典和授权配置，不得修改审计历史 |
| 系统管理员 | 系统运维与租户管理 | 运维权限与业务签发权限分离 |

用户必须属于当前项目并对所请求动作有权限。审批、签发、签收、整改确认和复查是不同权限点。角色矩阵需业务确认后实现。

## 3. 核心用户场景

### 3.1 单纯知识或现场咨询

用户以文字、图像或文件询问规范、施工现象或资料内容。系统给出基于来源的回答，不自动创建业务对象。若用户随后提出建档，应启动对应业务动作。

### 3.2 描述现场工作并建档

用户只用文字描述一项或多项工作，系统整理事项、识别表单候选、提取字段、显示缺失和冲突，确认后创建业务记录。纯文字路径必须与带附件路径共享意图、表单和写入规则。

### 3.3 多模态请求与多事项处理

用户在一条请求中组合文字、图片、文件。系统逐个解析证据，再形成零个或多个事项候选。附件数量不决定事项数或记录数。事项和证据可拆分、合并、移除、重新关联。

### 3.4 历史补录与日期冲突

用户可能在今天上传过去拍摄的照片，也可能用“今天”描述一个跨日旁站或多日工作。系统区分用户请求日期、证据日期和上传时间；展示冲突，让用户确认按哪个业务日期建档。

### 3.5 已有业务对象更新

用户补充某条记录、通知、台账或问题的资料时，系统须明确识别被引用对象。找不到唯一对象时列出候选或询问，不新建重复对象。所有修改保留版本和审计。

### 3.6 识别问题、整改通知及闭环

用户可以请求识别问题、登记问题、生成整改通知、签发通知或复查整改。每一步是独立动作和权限检查；识别建议不自动等于确认问题，登记问题不自动等于签发通知。

### 3.7 日志与月报

日志按业务日期聚合工作记录、材料、问题和其他已保存事实；月报按统计期聚合并包含模板要求的分表。聚合结果可追溯到来源并可编辑，审批归档前为草稿。

## 4. 功能需求

### FR-01 统一请求入口

系统应支持单条请求含文本、多个图片/文件、语音转写文本及历史流程引用；支持纯文本和纯附件。前端不得基于“是否有图片”选择业务流程。每条请求必须保存项目、用户、提交时间、时区和幂等标识。

### FR-02 附件管理

系统应保存原始资产元数据、内容哈希、MIME、大小、上传者、上传时间和处理状态。原文件只存于受控对象存储；访问遵循项目权限。附件可以被多个事项和业务对象引用，移除引用不得误删仍被引用的文件。

### FR-03 用户动作规划

系统应识别用户请求的动作、对象类型、时间范围、显式表式/事项类型、引用对象和是否要求写入。规划结果允许多动作、未知动作和歧义，不得强制压成单一意图。所有写入规划在执行前可被用户查看。

### FR-04 证据提取

系统按任务需要解析文字、图片、文档和语音，至少能为图片记录 OCR/水印字段、图像内容观察；文档记录可提取正文及页码/段落来源。每个字段值保留原始值、规范值、提取来源、处理器版本、置信状态和人工确认状态。

### FR-05 事项发现与编辑

系统应将请求中的工作事实整理成事项候选，并给出事项与证据关联及拆分依据。支持零事项、一事项、多事项；允许事项拆分、合并、重命名、修改时间/部位、证据移入移出、拒绝候选。事项数量不得由附件数量直接推导。

### FR-06 工作流及表式匹配

系统根据显式用户动作、事项事实、项目配置和已确认上下文提出业务流程/表式。找不到唯一适用项时询问用户；不因出现隐患词、材料词或水印就自动选择会产生副作用的流程。一次请求可匹配多个业务流程，但须列出动作清单。

### FR-07 表单草稿与验证

每种表式必须引用一个已发布 schema 版本。系统应将已知值映射到字段，执行类型、枚举、必填条件、跨字段、单位和日期校验；自动字段标明来源；缺失值保持空。字段证据和生成内容可查看、可编辑。签名和盖章字段只能走授权签章流程。

### FR-08 澄清交互

系统只询问会改变业务动作、记录数量、表式、日期或安全性的关键问题；每轮问题应清楚说明选项和影响。低风险可选字段允许稍后补齐；必填字段按表式规则阻止提交。用户回答必须绑定当前 workflow 与 draft version，不能误填另一条待办。

### FR-09 预览、确认和写入

确认界面必须展示将创建/更新的对象、表式、业务日期、核心字段、证据关联、缺失项、权限动作和不可逆后果。用户只能确认当前草稿版本。确认后由服务端重新校验权限、Schema 和状态，并以幂等命令写入。未确认草稿不写入正式对象。

### FR-10 工作记录

系统应为旁站、平行检查、巡视、验收、见证、危大巡视等分别维护类型和 schema。危大清单需根据类别/专业/配置版本选择。支持业务时间跨午夜。不同记录可以引用同一事项，但不得用不匹配表式的通用记录吞掉差异。

### FR-11 问题与隐患闭环

系统应将问题观察、人工确认、风险分类、整改通知草稿、通知签发、施工回复、监理复查和闭环状态分开管理。通知必须关联明确的问题及证据；签发前校验签发权限和法定字段；整改前后照片用途不同并保留关联。

### FR-12 通知、回复、联系单及会议纪要

系统应支持适用表式、编号、对象单位、正文、附件、签发/送达/回复/复查状态及关联。GD-B-215 与 GD-B-216 回复和复查必须可以追溯关联原通知。会议纪要应支持会议要素、与会单位/人员、决定事项和附件。

### FR-13 材料台账

材料按项目和批次管理。进场、取样、检测、验收、退场等是批次阶段信息；后续补充应更新或追加阶段事件，不应仅因重复上传文件创建重复批次。支持报审编号、报告及照片关联。

### FR-14 日志与月报生成

日志/月报从结构化业务对象和授权来源聚合。汇总数值由确定性查询计算；AI 生成的叙述必须能指向来源数据并标识为草稿。用户可调整来源范围和内容，审核签认后方可归档/导出正式文书。空数据不能伪装成“无问题”。

### FR-15 修改、取消、重试和更正

用户可在写入前取消或修改草稿；写入后按权限使用更正/撤销流程并保留审计。任务失败可重试且不能重复落库。已签发/归档对象不得无痕覆盖。

### FR-16 模板和 Schema 管理

管理员可发布带版本的表单定义、字段规则和模板绑定；发布前运行结构校验和样例回归。已使用版本不可删除。配置变更记录操作者、审批人、生效时间及回滚版本。

### FR-17 审计和可追溯性

系统应记录谁提交、谁确认、哪些证据/抽取值参与草稿、谁修改字段、谁写入/审批/签发/复查以及对应版本。用户可从表单字段回看来源；管理员可按项目和对象检索审计记录。

## 5. 业务规则

1. **载荷不定业务**：图片、文档、语音和文字均不隐含表式；附件能力由请求计划选择。
2. **数量不做映射**：N 个附件不等于 N 个事项；N 个事项也不必等于 N 张文书。
3. **动作分级**：识别、候选问题、问题登记、整改通知草拟、签发、复查是不同动作，分别受权限/确认控制。
4. **事实来源优先级可配置**：显式用户陈述、已确认项目资料、证据提取和模型推断要区分；冲突显式呈现，不静默覆盖。
5. **日期事实分离**：请求业务日期、拍摄/现场事件日期、上传时间、登记时间分开；相对日期使用项目时区。
6. **现场默认值不得冒充事实**：如模板或业务允许默认“符合要求”，必须由业务确认并显示默认来源；不能因字段为空自动判定无问题。
7. **多事项可关联多表**：同一事项可生成工作记录及关联问题/文书；每个副作用需在用户确认清单中明确列出。
8. **记录更正留痕**：签发和归档后的数据使用版本化更正，不能静默改写历史。
9. **未知不等于否**：无法识别人员到岗、检查结论或材料检测结果时保持未知，不自动填“否/合格”。
10. **用户选择可覆盖建议**：用户有权调整候选事项边界和表式；系统保留原建议及修改审计。

## 6. 非功能需求

- **正确性**：关键事实来源可追溯；关键字段未确认时不执行高风险写入。
- **可靠性**：异步任务可查询、重试、恢复；重复请求与重复确认幂等。
- **安全性**：项目级数据隔离，服务端授权，附件安全扫描/类型校验，传输和存储加密，操作审计。
- **可用性**：弱网下草稿和上传状态明确；失败不丢失用户输入；用户能恢复未完成流程。
- **性能**：接口快速返回受理状态；图像/OCR耗时与请求线程解耦；具体时延 SLO 在压测后由产品/运维确定。
- **可维护性**：表单版本、模型版本、提示模板版本和任务处理版本可追溯；业务逻辑可单测。
- **兼容性**：保留迁移期旧客户端/API兼容层；明确版本终止和迁移策略。
- **可访问性/易用性**：多记录草稿可逐条检查；重要日期、部位、对象、状态突出显示；不能只用颜色表达风险。
- **数据生命周期**：定义附件保留期限、归档、导出、删除/匿名化、备份恢复和审计保留政策。

## 7. 澄清与草稿呈现要求

澄清应按风险与影响排序：先确认“要执行哪种业务动作”，再确认“事项/记录拆分和目标表式”，再处理冲突日期/关键部位，最后补表式要求的字段。不得每次只机械问 Excel 下一行字段，也不得一次把所有字段缺项发给用户。

草稿列表每项至少展示：事项摘要、候选业务类型、业务日期/来源、地点/施工单位、证据缩略图、问题候选、字段完整度、冲突提示、确认状态。草稿动作支持逐条确认或整体确认；整体确认时必须说明包含哪些对象。

## 8. 验收标准与测试场景

### 8.1 统一入口

- 相同文字分别以纯文本、带图片和带文件提交时，意图解析遵循同一契约，不能因为附件存在就切换到固定业务。
- 附件处理失败时，用户仍可继续纯文本流程；失败证据不会伪装成已解析事实。
- 幂等重试返回同一请求/结果，不产生重复事项和业务记录。

### 8.2 日期、数量与事项分组

- 九张图片日期不同，用户说“记录今天的工作”：系统展示照片日期与请求日期冲突，不自动把九张图当九条今天的记录。
- 九张图片日期相同且内容相近：系统可提出同一事项候选，但不自动提交。
- 九张图同日但部位/活动不同：可提出多事项候选，说明分组证据，允许用户拆并。
- 一张图出现多个可辨事项：可关联多个候选事项，不复制或丢失原图。
- 无水印图片、OCR低可信或互相矛盾：字段标为未知/待确认，不编造日期/位置。
- 跨午夜旁站（如 19:12 至次日 08:12）：保存实际日期时间和时区，表单渲染不倒置时间。
- 用户明确按历史照片日期补录：每条事项日期按用户确认并保留来源。

### 8.3 业务动作和表式

- “看看图片有没有安全问题”：只输出识别候选，不创建记录或通知。
- “登记这批材料进场”：进入材料批次流程，不进入巡视。
- “生成今天监理日志”：从已授权且符合状态范围的记录聚合，不把每张照片生成记录。
- “根据问题拟一份通知”：生成关联问题的通知草稿；没有签发权限或用户确认时不签发。
- 用户未说明是巡视、旁站、验收或危大巡视且证据不能决定时，先澄清类型。
- 用户要求多种产物时，逐个展示记录/问题/文书动作和关系，分别校验权限。

### 8.4 表单/数据/安全

- 每个字段能显示来源、schema 版本和修改审计；模型建议与人工确认值可区分。
- 必填字段、枚举和跨字段约束在服务端生效；跳过选填字段不阻止草稿提交。
- 已发布文书能按原模板版本复现；新模板不改变历史输出。
- 无权用户不能签发、审批、复查或读取其他项目附件；前端绕过不影响服务端拦截。
- 同一通知的回复和复查始终关联原通知；材料后续检测结果更新原批次而不是重复建批次。
- 写入中断、部分附件关联失败、模型超时和用户取消均有可查询状态与恢复路径。

### 8.5 质量门槛

每个阶段上线前维护固定黄金集，分别评估动作解析、字段抽取、日期解析、事项分组、表式匹配、确认门控、领域写入、渲染和权限。高风险写入要求服务端规则测试 100% 覆盖关键转换；AI 指标阈值由阶段 0 基线和业务风险评估确定，不以单个整体准确率替代错误类型分析。

### 8.6 字段来源和模板差异

- 字段表标记“由系统生成”的项目，只有在对应来源已配置且当前用户/项目值有效时才能自动带出；无法取值应显示缺失，不能用空字符串、通用值或模型推测代替。
- 系统可从项目主数据带出姓名、单位和项目章主体信息，但不得把自动带出的姓名当作本人签名，也不得自动生成签章。签署动作必须经过授权签章能力或人工签认流程。
- 模板要求描述“问题及处理情况”时，证据未说明整改完成状态，应保持空/待补充。字段表中的默认“已按要求完成整改”等结论不能被当作无条件默认值。
- 模板内容、字段清单和填写样例不一致时，以经阶段 0 确认并发布的表式版本为准；未裁决差异必须可见，不能由模型自行选版本或隐藏差异。
- 日志/月报可以带出已保存且符合范围的记录；每段聚合文本和统计项应能回溯来源。若模板包含字段草稿未覆盖的部分，区分人工填写和自动聚合，不把缺少源数据写成“无事项”。
- 同一个正式模板可能包含多个子表或分册；系统须按模板目录保存其父子关系和各自版本，渲染/导出结果不能只生成主表而遗漏附件分表。

### 8.7 端到端主流程场景

| 场景 | 预期流程结果 | 不通过条件 |
|---|---|---|
| 只上传九张图片，不附文字 | 先询问用户目标；可完成图片识别和证据整理，但不建正式记录 | 按九张图直接建九条巡视或隐患记录 |
| “记录今天的工作”加九张不同日期照片 | 展示用户所说日期、各图可识别日期和冲突；提出可编辑的事项分组/日期候选 | 把上传日期当业务日期，或自动将九图定成九条今天的工作 |
| 九张同日同部位照片加“记录今天的工作” | 可建议同一工作事项并展示证据关系，继续询问表式或依据已确认上下文列出候选 | 因日期相同就默认单条巡视；因图片多就默认多条记录 |
| 九张图覆盖不同日期、区域或危大工程类型 | 生成有依据的候选分组，用户可拆分、合并和调整日期，再选择每项业务对象 | 仅按水印字段单因子拆分，或生成后不允许用户改组 |
| 多图中部分有水印、部分无水印 | 无水印图片仍参与人工可审阅的事项归组；水印字段来源及可信状态可见 | 将无水印证据丢弃，或复制邻近照片的日期/部位填入 |
| 用户只问照片是否有安全问题 | 返回风险观察与证据位置，说明需人工判定的部分 | 新建已确认隐患、生成通知或更改整改状态 |
| 用户请求建档但缺少动作/表式的决定性信息 | 询问一项能区分工作流的问题，并保留已提取事实供后续使用 | 每轮重跑并丢弃上下文，或一次性追问大量无关字段 |
| 用户确认多条草稿时有一条修改 | 只对已确认的草稿版本和动作执行；其余草稿保持待确认 | 用旧版本确认、重复创建，或把未确认项一并写入 |
