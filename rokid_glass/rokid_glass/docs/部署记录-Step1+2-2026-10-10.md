## 四、部署中发现并修复的两个真实缺陷

### 缺陷一：迁移脚本索引名写错（导致 preflight 中止）
- 现象：`--dry-run` 报「users 上找不到名为 `username` 的唯一索引」。
- 根因：生产实际唯一索引名是 **`ix_users_username`**（SQLAlchemy 生成），脚本误写为 `username`。
- 修复（本地 `scripts/`，已回读计数校验）：
  - `migrate_step1_org_role.py`：preflight 检查 + `DROP INDEX` 改 `ix_users_username`（新名出现 3 处，旧引用 0 残留）
  - `rollback_step1_org_role.py`：重建索引改 `ADD UNIQUE KEY ix_users_username`（1 处，旧引用 0 残留）
- 已编译通过（`py_compile` exit 0），重新上传后 dry-run 通过。

### 缺陷二：`audit_status`/`status` 被 `init_db()` 跳过（有全站 500 风险）
- 现象：reload 日志警告「跳过无法安全自动迁移的非空字段 `users.audit_status`、`projects.status`」。
- 根因：SQLAlchemy 2.0 中 `Mapped[str]` **默认 NOT NULL**；这两个字段只设了 Python `default=`、无 `server_default`，`init_db()` 的 `_reconcile_missing_columns` 按「非空且无 server_default → 跳过」规则不敢自动补列。
- 后果：production 这两列实际不存在，而模型要求非空 → 涉及 `users`/`projects` 的所有查询（含登录、`/me`）会报 1054 → **全站 500**。
- 修复：手动 `ALTER` 补齐（小表瞬时，无需停机）：
  ```sql
  ALTER TABLE users    ADD COLUMN audit_status VARCHAR(16) NOT NULL DEFAULT 'approved';
  ALTER TABLE projects ADD COLUMN status       VARCHAR(16) NOT NULL DEFAULT 'active';
  ```
- 复核：两列均 `EXISTS`。
- ⚠️ 后续建议：给这两个字段补 `server_default`，使其具备自举能力（当前生产已手动补齐，`init_db()` 重跑时列已存在、不会重复操作，暂无副作用）。

### 9.6 🔴 新发现的部署陷阱：bind mount + 重建目录 → 容器读旧文件

上传新前端产物时，**不能用 `rm -rf dist && tar xzf`**。

- 表现：宿主 `dist/` 已是新产物（`index-Bg_jyZok.js`），但 `docker exec rokid-nginx` 里
  `index.html` 的 mtime 仍是 **2026-08-15**（几个月前），nginx 一直吐旧页面。
- 原因：`rokid-nginx` 的 bind mount 绑定的是**创建容器时那个目录 inode**。
  `rm -rf dist` 后重建，宿主 inode 变了，容器仍指向已删除的旧 inode。
- 正确做法：**就地替换内容，保持目录 inode 不变**
  ```bash
  find dist -mindepth 1 -delete
  tar xzf /tmp/new.tar.gz --strip-components=1 -C dist
  ```
- 若已经 `rm -rf` 过：`docker restart rokid-nginx` 重新解析 mount 即可（本次即用此法恢复）。
- 校验方式：**不要只看 HTTP 200**，要 `docker exec rokid-nginx ls` 对比宿主与容器内的
  `assets/index-<hash>.js` 是否一致。hash 不一致 = 上传未生效。

## 十二、打开微信自助注册 + 邀请码可运营化（2026-10-10 13:15）

### 12.1 背景：注册链路一死一漏

盘点发现「注册」这件事在两条链路上完全不同口径，且都不可用：

| 链路 | 原状态 | 后果 |
| --- | --- | --- |
| Web `/auth/register` | 强制邀请码，角色取 `invite_codes.role` | `invite_codes` 生产 **0 行**、无任何创建代码 → **无码可填，完全不可用** |
| 小程序 `/miniprogram/auth/register` | 只查开关 + 角色白名单，**不校验邀请码** | 开关一开**任何人可自助注册** → 准入裂缝 |

### 12.2 三处配置/代码改动

**① 注册开关打开**（`.env` 改了不生效，必须重建容器——`config.py` 读的是容器进程环境变量）：

```yaml
# docker-compose.yml 第 81/82 行
ALLOW_PUBLIC_REGISTRATION: "true"
PUBLIC_REGISTRATION_ROLES: "inspector,special_supervisor"
```

```ini
# cloud-backend/.env 第 33/34 行
ALLOW_PUBLIC_REGISTRATION=true
PUBLIC_REGISTRATION_ROLES=inspector,special_supervisor
```

> 🔴 **发现**：生产 `.env` 的 `ALLOW_PUBLIC_REGISTRATION` **早就是 `true`**，但容器里读到的是 `false` ——
> 改 `.env` 文件不影响已在运行的容器，**必须 `docker compose up -d backend` 重建**。
> 服务名是 `backend`（不是容器名 `rokid-backend`）。

**② 修 `PUBLIC_REGISTRATION_ROLES` 中文旧值（静默失败 Bug）**

`get_public_registration_roles()` 用英文枚举集与配置做交集，配置是中文 → 交集为空 → 兜底：

```python
roles = [i for i in configured if i in valid_roles]   # [] （中文 ∉ 英文）
return roles or [UserRole.INSPECTOR.value]            # 退化为 ['inspector']
```

**静默失败**：白名单被清空，只剩 `inspector` 一个岗位，「专业监理工程师」无法注册。
改英文后 `/auth/roles` 正确返回两个岗位。

**③ 补邀请码管理接口（`auth.py`，权限 key `user_manage` = 仅超管）**

| 接口 | 说明 |
| --- | --- |
| `GET /auth/invite-codes` | 列表，含 `remaining` / `expired` / `used_by` / `role_label` 派生字段 |
| `POST /auth/invite-codes` | 创建；`role` + `level` + `max_uses` + `expires_in_days` + 可选自定义 `code`；不传自动生成 8 位易读码（排除 I/O/0/1） |
| `POST /auth/invite-codes/{code}/revoke` | 软停用（保留历史供审计） |

**两条硬约束**：

1. **邀请码不得发放公司级角色** —— 后端对 `ORG_ROLES` 显式拦截（400），
   否则会出现「拿到一个码即获得公司级权限」的越权面。公司级角色只能在用户管理里由超管授予。
2. **小程序注册改为与 Web 同口径**：`invite_code` 必填、**角色取自 `invite_codes.role`**
   （前端传的 `role` 一律忽略，杜绝自选岗位绕白名单）；邀请码 role 仍须在
   `PUBLIC_REGISTRATION_ROLES` 白名单内（双保险，白名单可随时收紧）。

注册成功才递增 `used_count`，用满自动 `is_active=False`；`GET /auth/invite-codes/validate`
只读不消耗次数（供注册页失焦回显岗位）。
