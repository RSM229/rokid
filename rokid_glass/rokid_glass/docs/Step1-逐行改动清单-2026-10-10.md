## 2. 已定路线：S2 · 三端同步改（用户 2026-10-10 拍板）

设计说明 §8.6 第 7 条原本写的是「出参用 `ROLE_LABELS` 转中文（**前端零改动**）」。核实后发现这句话**只对了一半**：出参能被后端兜住，但 `UserManage.vue:93` 的角色下拉是**前端硬编码中文**、`Ledger.vue:204` 是**中文比较**、`login/index.ts:28` 是**中文角色列表** —— 这些不跟着改就会 400 或判断失效。

**用户选择 S2：三端同步改成英文 key。** 因此：

- **后端不写中文兼容层**（不加 `@validates` 归一化、不做出参反转），`role` 的传输与存储**全链路英文 key**；
- 三端 48 处字面量全部替换为 key（清单见 §3.9）；
- 展示层的中文一律走**前端自己的 `ROLE_LABELS` 映射**（不再依赖后端转）。

> ⚠️ **代价（须知）**：S2 让"角色"概念在三端各存一份 key 字面量，**共 4 份**（后端枚举 + 三端）。将来加岗位要改 4 个地方。S1 只有后端 1 份。
> **缓解措施（已纳入本轮）**：三端各建**一个** `roleLabels.ts` 常量文件，所有 key↔中文映射只在那里定义，其余文件 import 引用 —— 把"4 份"压回"4 个文件各一份、且是同一份内容"。这比把字面量散在 48 处要好得多。

### 3.5 `app/models/user.py` — 权限判定（P0 核心）

**`has_permission`（`:74-78`）改造**：

```python
def has_permission(self, permission: str) -> bool:
    if self.is_super_admin():
        return True
    return permission in getattr(self, "effective_permissions", None) or \
           permission in ROLE_PERMISSIONS.get(self.role, [])
```

**新增 3 个方法**（`has_permission` 上方）：

```python
def is_super_admin(self) -> bool:
    """超管判据的唯一来源。取代散落的 username == 'admin'。"""
    return self.org_role == "super_admin"

def is_org_admin(self) -> bool:
    return self.org_role == "admin"

def is_org_level(self) -> bool:
    """是否持有任一公司级角色。"""
    return self.org_role in ("super_admin", "admin")
```

**设计要点**：`effective_permissions` 用 `getattr(..., None)` 兜住 —— Step 1 阶段该属性还不存在（Step 2 才在 `get_current_user` 里合成），所以退回按 `self.role` 查表，**行为与改前完全一致**。这保证 Step 1 是纯地基、可独立部署。

### 3.7.1 【问题 2 的正面回答】加与不加 `or is_org_admin()` 的区别

| | **(a) 加** `is_super_admin() or is_org_admin()` | **(b) 不加**（只留 `is_super_admin()`） |
| --- | --- | --- |
| **语义** | "公司级管理角色"＝超管＋管理员 | 只有超管能跨项目 |
| **现在的实际效果** | **完全相同** —— 生产 `org_role` 全为 NULL，无人是 `admin` | 同左 |
| **Step 2 之后的效果** | 公司级管理员**自动**获得上述 9 处跨项目能力 | 管理员**拿不到**任何一项；要跨项目必须再单独改 9 处 |
| **与 §7.4 定案的一致性** | ✅ 一致（成员增删开放给公司级管理员） | ❌ 不一致 —— 管理员点不进别的项目的成员列表 |
| **"行数"的诱惑** | 一行搞定 | 省一行，但 Step 2 要把同一文件再翻一遍 |

**结论（建议 (a)）：加。**

理由不是"省事"，而是**这两件事本来就是同一个判据**：`_can_manage_all_projects` 问的是"你是不是公司级管理者"，而 `org_role` 就是公司级角色的唯一载体。现在把它留成 `username == "admin"`，等于**在 Step 1 拆掉的那根分叉，从这 9 个调用点上原样长回来** —— 这正是设计说明 §8.3 反对"再放一个平行超管字段"的同一条理由。

**风险**：零。生产 5 个账号 `org_role` 全为 NULL，`is_org_admin()` 恒为 False，(a) 与 (b) 在**当前数据下行为逐位相同**。

> ⚠️ **一处需要单独留意**：`project.py:272` 的 `_require_project_scope` 若因 (a) 而放行管理员跨项目，**同时还要看它上面挂的 `require_permission("settings")`** —— 管理员是否有 `settings` 权限，取决于 §3.6 里 `ROLE_PERMISSIONS` 是否给 `org_role` 配了权限表。
> **本轮 `ROLE_PERMISSIONS` 只按"项目级岗位"索引，没有公司级角色的权限表** —— 公司级角色的权限来源是 `org_role` 分支（只给超管全量）。所以：
> **管理员要真正能调成员接口，还需要 Step 2 引入 `member_manage`**；本轮 (a) 只是把判据装好，**不会真的给管理员开门**。这正是 (a) 零风险的准确原因。

    WHEN '监理员'         THEN 'inspector'
    ELSE role END;

UPDATE invite_codes SET role = CASE role
    WHEN '总监理工程师'   THEN 'chief_supervisor'
    WHEN '总监代表'       THEN 'deputy_chief'

### 4.2 回退

反向 CASE 映射 + 清空新字段 + 约束回滚：

```sql
UPDATE users SET role = CASE role
    WHEN 'chief_supervisor'   THEN '总监理工程师'
    WHEN 'deputy_chief'       THEN '总监代表'
    WHEN 'special_supervisor' THEN '专业监理工程师'
    WHEN 'inspector'          THEN '监理员'
    ELSE role END;
-- project_members / invite_codes 同理

ALTER TABLE users    DROP INDEX uq_user_org_username;
ALTER TABLE users    ADD UNIQUE KEY username (username);
ALTER TABLE projects DROP INDEX uq_project_org_code;
ALTER TABLE projects ADD UNIQUE KEY code (code);

UPDATE users SET org_role = NULL, org_id = NULL, audit_status = 'approved';
```

> ⚠️ **回退有一个不可逆点**：`users.role` 若已出现**新岗位**（`documenter` / `witness` / `safety_supervisor`），反向 CASE 映射不到中文，会原样保留英文。回退脚本须**先检查这 3 个值的存在性并报错中止**，而不是静默留下脏数据。
> （另需检查的是"可能残留的中文"——若前滚 ⑤ 漏改，回退时会反向映射不到。共 **4 个值面** = 3 个新岗位 + 中文残留。）
