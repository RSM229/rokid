# 方案 B：手机号登录/注册 —— 实施步骤与决策清单

> 状态：**待决策**（尚未开工）
> 前置结论：当前系统**没有任何短信/验证码基础设施**，`users.phone` 只是 `String(20)` 可选文本字段，不参与身份校验。
> 本文档回答「上手机号登录需要哪些步骤」，供决策后再开工。

---

## 一、为什么不能「简单加个手机号登录」

常见误解：以为加个手机号输入框就算完成。**不行** —— 手机号作为身份凭证，前提是能证明「这个号是他的」。

当前 `POST /auth/register` 的 `phone` 字段是**用户自己填**、服务端**不校验归属**。若直接拿它当登录凭证：

| 攻击 | 后果 |
|---|---|
| 填别人的手机号登录 | 直接冒充他人身份，拿到其全部权限 |
| 遍历手机号 | 批量枚举已注册用户 |
| 撞库 | 与微信绑定链路混淆，出现一人多身份 |

所以**必须引入短信验证码**（或运营商一键取号）。这是方案 B 的本质成本，不是可选项。

## 二、三条可选技术路线

### 路线 B1：短信验证码登录（推荐起点）

**流程**：
```
用户输入手机号 → 点「获取验证码」→ 调 /auth/sms/send
  → 服务端校验频率/图形验证码 → 调短信服务商下发
  → 用户填 6 位码 → 调 /auth/sms/login（phone + code）
  → 校验通过 → 发 token
```

- 未注册手机号：可选择「自动注册」（需邀请码）或「提示联系管理员」
- 已绑定微信的账号：短信登录后仍走同一账号（按 `users.phone` 匹配）

**优点**：通用、不依赖微信、合规性好
**缺点**：要付费、要签名报备、有被刷短信风险（需频率限制）

### 路线 B2：运营商一键登录（本机号码校验）

微信小程序原生支持（`wx.login` + 运营商 SDK 或 `getPhoneNumber` 开放能力）。

- **小程序端**：`<button open-type="getPhoneNumber">` 可拿到用户手机号（**需企业主体 + 已认证小程序 + 该接口需付费**，微信按次收费）
- **优点**：无需短信、体验流畅、手机号由运营商保证可信
- **缺点**：仅小程序可用（Web 端无法用）；需微信开放平台配置；按次计费

### 路线 B3：仅手机号（不做验证）——**强烈不建议**

不验证归属等于无认证。仅适用于「内部完全可信网络 + 仅作展示用途」，不满足本项目（多企业入驻、外部用户）的安全要求。

## 三、路线 B1 详细实施步骤（若选它）

### 阶段 0：前置准备（外部依赖，非代码）

| # | 事项 | 说明 | 责任方 |
|---|---|---|---|
| 0.1 | 选定短信服务商 | 阿里云短信 / 腾讯云短信 / 华为云 | 业务方决策 |
| 0.2 | 企业实名认证 | 服务商侧企业资质审核 | 业务方 |
| 0.3 | 短信签名报备 | 如「【监理通】」，需 1-3 工作日审核 | 业务方 |
| 0.4 | 模板报备 | 验证码模板（含变量），需审核 | 业务方 |
| 0.5 | 获取 AK/SK | 写入后端密钥管理（**不进 git**） | 业务方 |

> ⚠️ 阶段 0 是**最长的关键路径**，且完全不受开发控制。建议先启动。

### 阶段 1：数据层（1 张新表 + 1 个字段约束）

```sql
-- 验证码记录表（SQLAlchemy 模型 + 迁移）
CREATE TABLE sms_verifications (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  phone         VARCHAR(20)  NOT NULL,
  code_hash     VARCHAR(128) NOT NULL,   -- 存哈希，不存明文
  purpose       VARCHAR(20)  NOT NULL,   -- login / register / bind / reset
  expires_at    DATETIME     NOT NULL,   -- 通常 5 分钟
  attempt_count INT          NOT NULL DEFAULT 0,  -- 防爆破
  used          TINYINT(1)   NOT NULL DEFAULT 0,
  client_ip     VARCHAR(45),
  created_at    DATETIME     NOT NULL,
  INDEX ix_sms_phone_purpose (phone, purpose),
  INDEX ix_sms_expires (expires_at)
);
```

- `users.phone` 需加**唯一索引**（多企业场景应为 `(org_id, phone)` 复合，与 username 同口径）
- 🔴 迁移脚本须上生产跑（本地 venv 是 Linux 的）

### 阶段 3：接口层（3 个新接口）

| 接口 | 作用 | 权限 |
|---|---|---|
| `POST /auth/sms/send` | 下发验证码 | 公开（带图形码/频率限） |
| `POST /auth/sms/login` | 手机号+验证码登录 | 公开 |
| `POST /auth/sms/bind` | 已登录账号绑定手机号 | 需登录 |

改造点：
- `login` 增加 `login_type`（password / sms）分支
- 登录白名单校验**必须与 `/auth/roles` 保持同口径**（本项目已踩过这个坑）
- 手机号登录与微信 `openid` 登录**共用同一 `users` 记录**（按 phone 匹配），避免一人两账号

### 阶段 4：三端改造

| 端 | 改动 |
|---|---|
| Web 后台 | 登录页加「手机号登录」Tab；账号设置加「绑定手机号」 |
| mobile-h5 | 同上 |
| 小程序 | 登录页加手机号登录；或接 `getPhoneNumber`（路线 B2） |

### 阶段 5：验证与上线

- 生产实测脚本（遵守项目「实测脚本铁律」：独立 session、finally 幂等复原）
- 频率限制压测（模拟刷码）
- 灰度：先对白名单开放

## 四、工作量与风险对比

| 维度 | B1 短信验证码 | B2 运营商一键登录 | B3 裸手机号 |
|---|---|---|---|
| 外部依赖 | 短信商资质+签名+模板审核 | 微信开放平台+企业认证 | 无 |
| 关键路径 | **签名/模板审核 1-3 工作日** | 微信配置 1-2 工作日 | 无 |
| 后端开发 | 高（服务层+接口+防护） | 中（对接 SDK） | 低 |
| 三端改造 | 中 | 仅小程序 | 低 |
| 持续成本 | 短信按条计费 | 微信按次计费 | 无 |
| 安全性 | 高 | 高（运营商保证） | **低（等于无）** |
| 覆盖端 | Web + H5 + 小程序 | **仅小程序** | 全端 |
| 主要风险 | 被刷码烧钱 | 仅小程序可用 | 冒充他人 |

## 五、决策建议

**若目标是「解决微信被占死、给用户一条不依赖微信的路」** —— 其实 **A 方案（微信绑定管理页）已经解决**了：超管解绑即可释放微信。手机号登录是**更大的独立需求**。

**若确实要上手机号**，建议：

1. **优先级**：先做 B1（短信验证码），它是通用基础；B2 可作为小程序端的体验增强后补。
2. **启动顺序**：**立刻启动阶段 0（短信签名报备）** —— 它是关键路径且不可控，代码可以并行写。
3. **最小可用版（MVP）建议范围**：
   - 只做「手机号 + 验证码**登录**」和「已登录后**绑定**手机号」
   - **不做**「手机号自助注册」（注册仍走邀请码，防止注册入口裂开）
   - 这样能把工作量压缩约 40%，且不影响现有准入体系
4. **复用现成设施**：`POST /auth/register` 已有 `phone` 字段，`users.phone` 已存在 → 只需加「验证」环节 + 唯一索引，不用新建用户表。
