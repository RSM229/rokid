## §1 一句话总结

把「项目内授权」从**全局单值 `users.role`** 改为**本项目成员表的岗位集合**（主岗 ∪ 附加岗），
在 `get_current_user` 单点注入合成结果，从而：

1. **修掉跨项目角色串权**（A 项目总监 → B 项目仍按总监授权）；
2. **修掉一人多岗表达不了**（同一项目既要当专监又要兼资料员）；
3. **分离上下文与归属**（`users.project_id` 只是会话上下文，`project_members` 才是归属真源）。

权限合成的唯一实现。**为什么不放进模型**：合成需要异步查询成员表，放进 `User` 会让模型层依赖 ORM 会话；独立函数也便于零依赖单测（本机无 sqlalchemy）。

| `roles_having_permission(perm)` | 反查持某权限的**项目级**岗位（排除公司级） |

| `member_user_ids_with_roles(db, pid, codes)` | 项目中持任一岗位的有效成员 id（通知投递用） |

## §3 模型层

### 3.1 `app/models/project_member.py`

补 **`extra_roles`** 列（Step 1 漏做，设计说明 §8.4 Step 1 第 3 条明确要求）：

```python
extra_roles: Mapped[list | None] = mapped_column(
    JSON, nullable=True, comment="附加岗位列表（不含排他岗位）"
)
```

补 `role_codes()` 方法（主岗 + 附加岗，去重、过滤空值与非法元素）：

```python
def role_codes(self) -> list[str]:
    codes: list[str] = []
    if self.role:
        codes.append(self.role)
    for item in self.extra_roles or []:
        if isinstance(item, str) and item and item not in codes:
            codes.append(item)
    return codes
```

同时把 `role` 的注释从「入会时角色快照」升级为「**本项目主岗（授权真源）**」——
这是 Step 2 的语义核心：该字段从"没被读过"变成"项目内授权唯一依据"。

> ⚠️ **为什么补在 Step 2 而不是回改 Step 1**：`extra_roles` 属 schema 变更，而 Step 1 已定「schema 变更全集中 Step 1」。
> 但 Step 1 已实施完毕（本地未部署），回改将导致 Step 1 清单与产物不一致。故在 Step 2 开头补做并在此**显式记录**，
> 而非静默处理。部署时两步必须**同窗口一次部署**。

### 3.2 `app/models/user.py`

1. **新增公司级权限 key 进 `ROLE_PERMISSIONS`**（否则 `permissions_for_roles(org_role)` 取不到）：

```python
ORG_ROLE_SUPER_ADMIN: ["project_create", "project_edit", "user_manage",
                       "user_approve", "role_grant", "member_manage"],
ORG_ROLE_ADMIN:       ["user_approve", "member_manage"],
```

2. **总监补 `member_manage`**（项目级）：总监在本项目内可增删成员。
3. **新增 `ORG_LEVEL_PERMISSIONS`**：`frozenset` 标记公司级 key，供 `_require_project_scope` 等区分两层。

### 4.1 `app/routers/auth.py` — `get_current_user`

```python
async def get_current_user(token=Depends(oauth2_scheme), db=Depends(get_db)) -> User:
    user = await get_user_from_token(token, db)
    from app.services.permissions import attach_effective_permissions
```

## §8 账号管理权限 key 修正（本轮新增决策）

**发现的问题**：账号管理 4 接口全挂业务 key `settings`，而「总监理工程师」恰好持 `settings`
→ **总监能在自己项目内建号、设任意角色（含再建一个总监）、改他人密码** = 真实越权。

**处置**（2026-10-10 用户确认，选"按设计说明改"）：

| 接口 | 改前 | 改后 |
| --- | --- | --- |
| `GET /auth/users`（列表） | `settings` | **保留 `settings`**（只读查看；总监看本项目同事） |
| `POST /auth/users`（建号） | `settings` | **`user_manage`** |
| `PUT /auth/users/{id}`（改信息） | `settings` | **`user_manage`** |
| `DELETE /auth/users/{id}/wechat-binding` | `settings` | **`user_manage`** |

> 注：生产 `admin` 账号的 `org_role` 实测为 `super_admin`（`init_default_users.py:89`），
> 故本次改动**不改变生产 5 账号的可用性**；纯属修掉总监越权。
