# Agent 隐患候选与统一证据入口（第四阶段）

## 1. 阶段目标

第三阶段已经完成工作记录的多事项规划、聊天内确认和批量建档，但仍有几条旧链路绕过统一责任边界：

- 隐患识别命中后由前端关键词决定是否建档；
- 隐患通过逐张 HTTP 请求写入，失败时可能出现部分成功；
- 记录补照片、聊天内表单补照片存在直接生成整理计划的入口；
- 用户补充日期、地点等事实仍由前端正则合并。

本阶段的目标是消除这些旁路，让“识别、候选、确认、正式写入”在隐患业务中也遵循同一原则：

> 模型与视觉能力只提出候选，服务端负责校验、数量和事务边界，用户确认后才写正式业务数据。

## 2. 责任划分

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 前端 | 展示证据、候选和表单；收集用户选择；调用受控接口 | 判断是否建档；决定隐患条数；逐条写正式记录 |
| 请求计划器 | 理解用途、抽取用户事实、建议记录类型和附件用途 | 执行写入、决定正式记录数量、绕过权限 |
| 水印/EXIF/视觉能力 | 提供客观字段和风险观察 | 把观察直接当成正式隐患 |
| 隐患候选服务 | 校验候选项、去重、限制批量大小、拒绝非隐患结果 | 写数据库 |
| 隐患路由 | 锁定媒体、校验归属、原子创建隐患与影像关联、审计和通知 | 依赖前端关键词或模型自由裁量 |
| 用户 | 勾选候选、排除误报、最终确认 | 重复填写系统已经读取到的证据 |

## 3. 隐患主流程

```text
用户上传图片并明确要求检查隐患
  -> request-plan 判断 needs_hazard_analysis
  -> 水印/EXIF + 通用图片观察 + 隐患视觉模型
  -> 生成本轮隐患候选（不创建 Hazard）
  -> 聊天内展示每个候选的风险、照片、部位和依据
  -> 用户勾选需要建档的候选，或排除误报
  -> 前端把图片登记为统一媒体证据（MediaRecord）
  -> POST /hazard/commit-candidates
  -> 服务端锁定并校验本次全部 media_id
  -> 同一事务创建 Hazard、关联 ImageRecord、更新 MediaRecord
  -> 全部成功才提交；任一失败整批回滚
```

### 3.1 候选数据结构

候选项是会话内的可操作视图，不是正式隐患记录：

```ts
interface HazardCandidateView {
  id: string
  image: string
  title: string
  riskCategory: string
  evidence: string[]
  section: string
  location: string
  weather: string
  takenAt: string
  detection: Record<string, unknown>
  selected: boolean
  status: 'pending' | 'committing' | 'committed' | 'discarded'
}
```

正式写入只读取用户勾选的 `pending + selected` 项。排除项继续保留在会话里作为“看过但没有建档”的痕迹。

### 3.2 服务端提交契约

`POST /hazard/commit-candidates`

```json
{
  "candidates": [
    {
      "media_id": 123,
      "detection": {
        "has_hazard": true,
        "risk_status": "存在隐患",
        "risk_category": "临边防护",
        "top1_risk": "三层东侧临边防护缺失",
        "evidence": ["未设置防护栏杆"]
      },
      "section": "三层东侧",
      "location": "3号楼",
      "weather": "晴",
      "taken_at": "2026-10-18T09:30:00",
      "remark": "用户确认建档"
    }
  ]
}
```

服务端硬约束：

- 一次 1 至 20 条，`media_id` 不得重复；
- `detection.has_hazard=true` 或 `risk_status=存在隐患`，否则拒绝；
- 图片必须属于当前用户、当前项目，且尚未关联其他业务；
- 任一张图片关联冲突时整批拒绝；
- 正式写入使用单个数据库事务，不做逐张提交；
- 写入成功后才发实时事件，通知失败不回滚已成功的业务事务。

## 4. 统一证据入口

以下入口都必须先经过 `POST /agent/request-plan`：

1. 主聊天一次上传多张图片或多个文件；
2. 给已有工作记录补照片时发现水印冲突；
3. 聊天内结构化表单附带照片提交。

前端只负责把水印、EXIF、通用图片观察、文件文本转换成统一证据结构。证据结构中的 `field_sources` 保留来源，不能用视觉推断冒充水印事实：

```json
{
  "kind": "image",
  "observed_date": "2026-10-18",
  "observed_date_source": "watermark",
  "project": "示例项目",
  "location": "3号楼",
  "section": "二层东侧",
  "field_sources": {
    "record_date": "watermark",
    "project": "watermark",
    "location": "watermark",
    "section": "watermark",
    "weather": "watermark"
  }
}
```

## 5. 多轮补充规则

第四阶段移除了页面里的日期、地点正则合并。用户对当前草稿继续补充时，前端把“已有整理要求 + 本轮补充”和全部已有证据重新交给服务端计划器：

- 服务端重新输出事实、冲突和 `item_plan`；
- 前端不再自行从文本中切日期或地点；
- 记录类型已经确认时，用户选择优先保留；
- 服务端生成新事项后，只对证据集合完全一致的事项保留已有表单字段；
- 服务端未能可靠重构事项时，不覆盖已有草稿，并明确提示补充信息；
- 事项数量继续由服务端 `item_plan` 决定，前端不根据图片数量或字符串相似度自行拆分。

## 6. 交互要求

- 隐患结果直接显示在聊天回复下方，不跳转页面；
- 每个候选都有图片、风险名称、类别、部位、依据和当前状态；
- 支持逐项勾选、排除误报和一次确认所选项目；
- 识别阶段明确显示“尚未创建正式隐患记录”；
- 建档期间显示候选级状态，成功后显示正式隐患编号；
- 模型回答不得声称“已保存/已建档”，除非服务端批量接口已成功返回。

## 7. 失败与重试

### 图片登记失败

只产生未关联业务的媒体证据，不创建隐患。用户重试时，已经拿到 `media_id` 的候选直接复用，避免重复上传。

### 批量写入失败

整个事务回滚，所有候选回到可重试状态并显示错误原因。不会出现“九条里成功三条”的部分成功。

### 通知失败

业务事务已经提交，通知属于提交后的旁路，不允许因为推送失败把正式记录报成失败。

## 8. 本阶段完成项

- 删除前端 `wantsRecordIntent()` 关键词建档判断；
- 删除前端逐图调用 `/hazard/commit-detection` 的隐式写入；
- 新增隐患候选校验服务与批量事务接口；
- 新增聊天内隐患候选卡；
- 记录补照片冲突入口纳入 `request-plan`；
- 聊天内表单补照片入口纳入 `request-plan`；
- 移除 `extractReviewFacts()` 前端日期/地点正则；
- 增加“服务端事项计划不可用时不得覆盖已有草稿”的保护；
- 增加前端防回归测试和后端候选校验测试。

## 9. 后续可以继续演进的部分

- 将隐患候选计划本身落成独立、可恢复的业务草稿，而不是只存在当前聊天视图；
- 为请求计划、用户确认、工具执行和事务结果增加独立审计表；
- 当需要长流程中断恢复时，再评估流程引擎；当前业务边界不依赖 LangChain 或 LangGraph；
- 将表单字段定义进一步版本化，并统一携带 `value/source/status/confidence`；
- 把表单生成与工作记录拆开，坚持“先建记录，按需生成 Word/PDF/统表”。
