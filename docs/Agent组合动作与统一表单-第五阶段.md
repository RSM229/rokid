# Agent 组合动作与统一表单（第五阶段）

## 1. 本阶段目标

本阶段解决两个会直接影响小程序体验的问题：

1. 同一请求同时需要整理工作记录和分析安全隐患时，不能只执行其中一个分支。
2. 追问和补字段不能同时存在两套表单协议，也不能把下拉选项索引当成业务值提交。

本阶段仍然遵守既有写入边界：模型给出语义候选，服务端确定动作和字段，前端只展示受控流程，正式业务记录必须经过用户确认。

## 2. 组合动作

请求计划可以同时包含：

- `record_work`：整理工作记录候选。
- `analyze_hazard`：调用隐患视觉能力并形成待确认候选。

前端收到这类计划后，在同一轮对话中生成两个并列结果：

```text
用户消息 + 图片/文件
  -> 服务端请求计划
  -> 工作记录事项候选（等待用户确认）
  -> 隐患识别候选（等待用户单独勾选确认）
```

两条流程不共享正式写入动作：

- 工作记录由事项计划确认后批量落库。
- 隐患由用户勾选候选后调用原子批量接口落库。
- 未确认的识别结果只作为证据和候选保留。
- 两个结果可以连续出现，但不会把同一业务事实静默写入两类正式记录。

这样处理的原因是：一个请求可以同时包含“记录这次工作”和“检查是否有危险”，但“工作记录已创建”不等于“隐患已成立”，两个确认边界必须分开。

## 3. 统一表单协议

聊天内只保留一种渲染入口：`AgentForm`。后端新响应直接返回该结构；旧版 `input_components` 如果仍然出现，前端会在进入消息列表前转换成同一种字段结构。

表单顶层包含：

- `schema_version`：客户端渲染协议版本。
- `field_schema`：字段定义来源，例如 `record_field_spec.v1`。
- `form_code`：省统表或业务表编码，未确定时为空。
- `kind`：记录类型选择、工作记录、附件补充或普通表单。
- `fields`、`filled`、`attachments`、`actions`：可编辑字段、已读取字段、附件任务和后续操作。

字段由 `record_field_spec` 生成时带：

- `key`：模板字段键。
- `canonical`：服务端规范字段名。
- `definition_source`：定义来源。
- `required`、`control`、`options`、`section`、`hint`。

旧输入组件不再单独渲染，也不再为每个字段生成一个独立提交按钮。所有字段在同一个聊天内表单中一起填写、一次提交。

## 4. 选择控件修复

微信 `picker` 的选择事件返回的是选项索引，不是选项文本。此前代码直接保存索引，可能把“天气：晴”提交成 `0`。

现在选择控件按以下规则处理：

```text
select   -> options[event.detail.value] -> 保存选项文本
date     -> 保存日期文本
其他控件 -> 保存用户的原始输入
```

字段最终提交前仍由服务端按字段表归一化，不能依赖前端猜测业务字段名。

## 5. 数据流与边界

```text
用户文字/图片/文件
  -> 水印、EXIF、图片观察等客观证据
  -> 服务端 request_plan
  -> 工作记录 item_plan
  -> 聊天内 AgentForm 补齐字段
  -> 用户确认事项
  -> 服务端事务批量创建记录

同一 request_plan
  -> needs_hazard_analysis
  -> 隐患视觉候选
  -> 聊天内逐项勾选
  -> 原子批量接口创建隐患
```

约束：

- 图片上传本身不代表任何业务类型。
- 记录类型未确认时不能写正式记录。
- 隐患识别结果未勾选时不能创建正式隐患。
- 低置信度字段、冲突字段和未知字段保持显式状态，不能被表单默认值吞掉。
- 表单字段值最终以服务端字段表校验为准。

## 6. 当前实现

后端：

- `_agent_form` 返回表单协议版本、字段定义来源和模板字段键。
- `field_view` 保留 `key` / `canonical` / `definition_source`。
- 旧 `input_components` 继续作为兼容响应保留，但不再是前端主渲染协议。

小程序：

- 组合请求追加共享的隐患候选消息，不再因为工作记录分支提前返回而丢失隐患结果。
- 旧输入组件在 `agentReplyToMessage` 中转换成 `AgentForm`。
- 删除第二套旧输入表单模板和样式。
- 修复选择控件把索引写入字段值的问题。

## 7. 验收用例

1. 用户上传现场图片并说“记录今天的工作，同时看看有没有安全问题”。
   - 结果：出现工作记录候选和隐患候选；两者分别等待确认。
2. 用户只要求“看看有没有隐患”。
   - 结果：只出现隐患候选，不出现工作记录确认按钮。
3. 用户选择天气“晴”。
   - 结果：提交值为“晴”，不是 `0`。
4. 服务端仍返回旧 `input_components`。
   - 结果：小程序以统一表单渲染，不再显示每项独立提交按钮。
5. 表单只补齐部分字段。
   - 结果：已读取字段保持回显，缺失必填字段继续留在同一张表单内。

## 8. 后续边界

本阶段没有引入新的流程引擎，也没有改变正式记录的原子写入规则。请求追踪表、跨重启的完整流程实例和更细的字段来源审计仍属于后续基础设施工作；当前事项计划、草稿版本和用户确认版本先承担恢复与审计职责。
