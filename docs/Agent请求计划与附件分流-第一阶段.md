# Agent 请求计划与附件分流：第一阶段

## 1. 目标

把附件处理从“前端按关键词决定业务分支”改为“证据先统一准备，后端生成受控请求计划，再决定后续能力”。

本阶段只解决请求入口和候选计划，不直接创建正式记录。记录条数、字段冲突和表式仍由事项规划、草稿确认和执行阶段处理。

## 2. 责任边界

### 模型负责

- 理解用户原话和上下文
- 提出一个或多个业务动作候选
- 从受控目录中选择记录类型
- 说明候选依据和置信度

### 服务端负责

- 动作白名单和记录类型归一化
- 澄清字段和确认边界
- 判断计划是否允许进入执行
- 工具权限、参数、落库和审计

### 前端负责

- 上传图片和文件
- 调用 OCR、EXIF 和通用图片观察
- 渲染后端返回的计划、草稿和表单
- 收集用户确认和修改

前端不再决定“上传图片就一定识别隐患”或“记录工作就一定创建巡视记录”。

## 3. 请求计划

接口：`POST /api/agent/request-plan`

核心字段：

```json
{
  "schema_version": 1,
  "intent": "create_record",
  "actions": [
    {
      "id": "record_work",
      "confidence": 0.9,
      "reason": "用户明确要求记录现场工作"
    }
  ],
  "record_type": "巡视",
  "record_type_confidence": 0.86,
  "needs_hazard_analysis": false,
  "attachment_purposes": ["work_evidence"],
  "clarifications": [],
  "choice": [
    {"value": "record_type:巡视", "label": "巡视记录", "kind": "record"},
    {"value": "record_type:旁站", "label": "旁站记录", "kind": "record"},
    {"value": "record_type:验收", "label": "验收记录", "kind": "record"},
    {"value": "record_type:见证", "label": "见证记录", "kind": "record"},
    {"value": "archive_only", "label": "仅整理归档", "kind": "archive"}
  ],
  "selected_tool": "create_work_record",
  "execution_mode": "single_tool",
  "write_allowed": false,
  "requires_confirmation": true,
  "reason": "",
  "degraded": false
}
```

约束：

- `actions` 只能使用服务端目录中的动作 id。
- `record_type` 必须归一化为 `巡视/旁站/验收/见证` 之一。
- 上传图片本身不能触发 `analyze_hazard`。
- 多个业务动作不会被压缩成单个工具调用。
- `write_allowed` 在计划阶段始终为 `false`。
- 存在未解决澄清时，`execution_mode` 必须为 `clarify`。
- 模型失败时返回安全澄清计划，不推断记录类型，不自动写库。

## 4. 附件处理流程

```text
附件
  -> 水印/OCR、EXIF、通用图片观察、文件解析
  -> 结构化证据摘要
  -> /agent/request-plan
  -> 根据需要执行隐患分析能力
  -> 工作记录事项草稿 / 普通对话 / 查询 / 澄清
  -> 用户确认
  -> 服务端执行写入
```

“记录今天的工作”但没有说明记录类型时，计划应保留图片和已提取事实，并要求用户选择巡视、旁站、验收、见证或仅归档。

“巡检”作为“巡视”的业务同义表达时，由统一记录目录归一化为“巡视”，不再依赖页面路由或分散词表。

## 5. 当前不变量

- 用户明确陈述优先于水印、图片观察和模型推断。
- 图片识别失败不代表用户没有提供信息。
- 附件数量不等于记录数量。
- 隐患分析结果不等于正式隐患记录。
- 未确认的事项草稿不进入正式业务表。
- 任何模型输出都不能绕过工具权限、项目范围和审计。

## 6. 验证范围

- 记录类型同义词归一化
- 模糊记录请求必须澄清类型
- 仅上传附件不触发隐患分析
- 明确隐患请求才启用隐患分析
- 无附件时要求补图
- 多动作计划保留但不自动执行
- 非法动作被丢弃且降级为澄清
- 计划器失败时保持零写入

## 7. 后续阶段

1. 字段级事实、证据、冲突和来源优先级统一进入请求结果。已在第二阶段完成。
2. 建立独立事项规划器，确定零条、一条或多条记录。已在第二阶段完成。
3. 后端返回结构化聊天内表单和确认版本。
4. 将全部写操作迁入草稿确认与事务执行链路。
5. 增加请求追踪、金标准数据集和模型版本回归评测。

第二阶段说明见 `Agent语义事实与事项候选-第二阶段.md`。
