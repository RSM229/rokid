## 0. 一句话说明

把「角色能做什么」从代码常量变成可以在后台配置的数据，并保证三件事：
**改不坏**（有目录与兜底）、**改不越权**（不能授予自己没有的权限）、**改完就生效**（前后端都是）。

---

## 1. 三个关键设计判断（含一次踩坑修复）

### 1.1 超管的「全量」必须来自独立目录，不能来自矩阵并集

原实现 `ALL_PERMISSIONS = ⋃ ROLE_PERMISSIONS.values()`。矩阵一旦可配，
把某个权限从**所有**角色上取消勾选 → 并集丢掉该键 → **超管也失去它**
→ 没有任何人能再把它配回来 → **权限系统锁死**。

修复：新增 `permission_catalog.py` 作为权限键的权威清单，超管取目录全量。

### 1.2 角色 key 锁定，只配权限

`project_members.role` 存的是角色 key，后端几十处逻辑在拿 `UserRole` 枚举比较。
若允许界面新增角色，DB 里多出来的 key 会变成"幽灵角色"——不报错、也不生效。
因此 `roles` 表只允许改**中文名 / 排序 / 启用 / 权限**，key 由代码枚举播种。

### 1.3 顺手修掉一个静默缺陷：孤儿权限键 `signature_manage`

Web 前端路由用 `signature_manage` 门控「签章管理」页，但**后端权限矩阵里
从来没有这个键** → 除超管（`is_super_admin()` 短路）外，**所有人都进不去该页面**，
且不报任何错（守卫只是静默重定向到工作台）。

修复：收编进权限目录，默认授予 `chief_supervisor` / `deputy_chief` /
`special_supervisor`（需要签署文书的岗位）。

> ⚠️ **这是本轮唯一的对外行为变更**：这三个角色现在能看到「签章管理」菜单了。
> 如果你希望维持"仅超管可见"，上线后在「角色权限」页把这一格取消即可。

## 4. Schema 变更

**只有新增两张表，不改动任何既有表**（无 `ALTER`、无回填、无需停机）：

```
roles              id, key(唯一), label, is_org_level, sort_order, enabled,
                   perm_version, created_at, updated_at
role_permissions   id, role_key(索引), permission_key, updated_by, updated_at
                   UNIQUE(role_key, permission_key)
```

## 5. 安全约束（后端强制，前端同步灰显）

| # | 约束 | 落点 |
| --- | --- | --- |
| 1 | 只有 `role_grant` 能改权限 | `require_permission("role_grant")` |
| 2 | 不得授予自己没有的权限（超管豁免） | PUT 校验 `set(wanted) - set(user.permission_set())` → 403 |
| 3 | 项目级角色不得持有公司级权限 | PUT 校验 `ORG_ONLY_PERMISSION_KEYS` → 400 |
| 4 | 权限键必须在目录内 | `validate_permission_keys` → 400 |
| 5 | 禁止编辑 `super_admin`（恒全量） | PUT 显式拒绝 → 400 |
| 6 | 每次变更写 `security_audit` | `action="role_permission_update"`，含 added/removed/remark/version |

## 6. 部署与验收

### 6.1 部署步骤

1. **只读预检**（新表是否存在、现有账号/角色分布）
2. 上传后端改动文件（bind mount，uvicorn 自动重载）
3. 服务器上 `python scripts/migrate_step3_roles.py --dry-run` → 再 `--yes`
4. 校验：两张表行数（期望 `roles` = 9、`role_permissions` = 某值）
5. 前端 `dist` **就地替换**（保 inode），校验容器与宿主 hash 一致
6. 接口验收（见下）

### 6.2 验收清单

- [ ] `roles` 9 行、`role_permissions` 与代码种子一致
- [ ] `GET /api/permissions/matrix` 超管 200，总监 403
- [ ] 改动某角色权限 → 该角色用户**下一个请求**即拿到新权限（`X-Perm-Version` 变化 → 前端自动刷新菜单，无需重登）
- [ ] 越权三连：项目级角色勾公司级权限 → 400；目录外键 → 400；改 `super_admin` → 400
- [ ] 变更在 `security_audit` 留痕
- [ ] `GET /auth/roles`（登录页）与矩阵同口径
- [ ] 既有功能回归：4 角色登录、`/auth/me`、派单（`task_receive` 反查）、成员管理
- [ ] 清空测试改动（恢复默认）后无残留

### 6.3 回滚

- **权限配置回滚**：界面「恢复默认」按钮，或 `POST /api/permissions/matrix/reset`
- **代码回滚**：还原改动文件即可（新表留着不影响，读路径在表为空时走代码常量）
- 无 schema 破坏性变更，**不需要数据库回滚**

## 7. 已知边界（明确不做）

| 事项 | 说明 |

| 自定义角色 | 按决策**锁定 key**，界面只能改权限/名称/排序 |
