# Agent 事项确认与批量执行：第三阶段

## 1. 阶段目标

第二阶段已经形成 `RequestPlan -> Facts -> ItemPlan`。本阶段把这条链路接到真实业务草稿和正式工作记录：

```text
统一请求
  -> 服务端动作与事实候选
  -> 服务端事项计划 item_plan
  -> 聊天内可编辑 ReviewPlan
  -> 用户确认
  -> 服务端版本校验
  -> 同一事务批量创建 WorkRecord
```

本阶段完成后，事项数量不再由页面重新推断。小程序只负责展示、收集修改和执行用户操作，后端仍拥有事项候选、字段来源、确认和写入边界。

## 2. 责任划分

### 模型与规划器

- 理解用户表达并提交动作、记录类型和事实候选。
- 结合水印/EXIF、通用图片观察和用户描述形成事项候选。
- 说明字段冲突、缺项和推荐记录类型。

### 服务端

- 控制可用动作、记录类型和工具目录。
- 按日期、项目、地点、部位生成零个、一个或多个事项。
- 保存字段来源、缺项、冲突和请求计划快照。
- 校验资料归属、用户权限、项目范围、修订版本和媒体归属。
- 在确认后的单一事务中批量创建正式工作记录。

### 小程序

- 上传图片、文件和补充信息。
- 渲染服务端事项计划和证据。
- 在聊天内完成字段补充、事项合并、事项拆分、照片重分配和删除。
- 提交用户的精确草稿版本进行确认，不在前端决定最终记录数量。

## 3. 从 ItemPlan 到 ReviewPlan

服务端 `item_plan` 使用证据下标关联图片：

```json
{
  "items": [{
    "id": "item_1",
    "record_type": "巡视",
    "fields": {
      "record_date": {"value": "2026-10-19", "source": "watermark", "status": "evidence_extracted"},
      "section": {"value": "3号楼二层", "source": "watermark", "status": "evidence_extracted"}
    },
    "evidence_indexes": [0, 1, 3],
    "missing_fields": ["location"],
    "issues": [],
    "status": "candidate"
  }],
  "unassigned_evidence_indexes": [2],
  "issues": []
}
```

小程序通过单一适配函数完成以下转换：

- `items[].id` 转为稳定事项 ID。
- `evidence_indexes` 转为已经上传的媒体 ID。
- `fields[].value/source/status` 转为草稿字段和来源。
- `missing_fields`、`issues`、事项状态原样保留。
- 未被事项或待分配列表覆盖的证据自动进入待分配区，确保每份证据只出现一次。
- 整个 `request_plan` 作为不可变快照写入草稿，供确认和执行审计使用。

适配器不按图片数量、日期或关键词重新分组。

## 4. 聊天内编辑

聊天卡是业务操作面，不是跳转入口。用户可以直接完成：

- 修改工作名称、地点、施工部位和工作描述。
- 选择或修改业务日期。
- 从服务端推荐记录类型中采用一个，或选择其他类型。
- 修改单张图片的水印字段和备注。
- 勾选多个事项后合并。
- 从多图事项中拆出单张图片成为独立事项。
- 把图片移出事项，保留到待分配区。
- 把待分配图片加入已有事项，或直接创建新事项。
- 删除事项并把其证据释放到待分配区。

所有修改都会递增本地草稿版本，并按服务端修订号串行保存。任何修改都会清除旧确认状态。

## 5. 缺项与冲突

事项包含 `missing_fields` 时，聊天卡直接显示待补字段，并提供对应输入控件。缺项是候选完整度提示，不直接等同于用户未提供；字段是否可信仍由 `source` 和 `status` 决定。

水印或 EXIF 成功识别的日期、项目、地点、部位和天气优先于冲突的用户转述。冲突双方同时保留：

```json
{
  "field": "record_date",
  "user_value": "2026-10-18",
  "evidence_values": ["2026-10-19"],
  "preferred_value": "2026-10-19",
  "preferred_source": "watermark_or_exif",
  "status": "conflict"
}
```

水印没有提供某字段时，回退用户描述。通用视觉观察不能冒充水印客观字段，也不能覆盖用户明确时段。

## 6. 记录类型确认边界

草稿允许以“待定”类型保存并继续沟通，但正式执行要求每个事项都有明确的记录类型：

- 前端确认按钮在类型未定时保持不可用。
- 后端 `review_issues()` 再次检查类型，防止绕过前端。
- 执行器只接受受权限控制的记录类型，并再次验证角色权限。

这避免产生无法进入后续表式流程的“待定工作记录”。

## 7. 确认与批量执行

确认和执行使用两个明确命令：

```text
POST /agent/review-plans/{id}/confirm
POST /agent/review-plans/{id}/execute
```

确认命令绑定精确的 `revision`。执行命令只接受同一修订号，并再次执行：

- 计划结构校验。
- 资料完整归属校验。
- 项目与用户范围校验。
- 媒体归属和重复挂接校验。
- 记录类型和角色权限校验。

执行阶段在同一数据库事务内创建全部 `WorkRecord`。任一事项失败时不提交部分记录。记录初始状态为草稿，便于用户进入工作记录继续核对；PDF、Word 和正式表式按需生成，不在建档时自动触发。

## 8. 多轮建档

同一用户、项目和会话只保留一条整理计划记录，用于稳定修订和审计。状态流程为：

```text
draft -> confirmed -> executed
```

执行完成后，用户在同一会话发起新的整理请求时，复用该计划行开启下一修订：

- 递增 `revision`。
- 重置为 `draft`。
- 清空本轮确认和执行结果。
- 已创建的工作记录不受影响，仍通过 `content_json.review_plan_id/revision` 保留来源。

新修订不能覆盖此前已经落库的业务记录。

## 9. 失败与恢复

- 规划失败：图片仍保留在待分配区，用户可以重新选择用途。
- 字段冲突：候选采用客观来源值，同时展示原始值。
- 保存冲突：服务端修订号不匹配时拒绝覆盖，客户端重新加载。
- 确认过期：任何字段、证据归属或记录类型变化都会使确认失效。
- 执行重复：同一已执行修订可幂等返回之前结果。
- 部分媒体异常：在执行前完成全部媒体校验，不进入写记录循环。

## 10. 验证范围

本阶段测试覆盖：

- 后端 `item_plan` 无重新分组地映射为聊天草稿。
- 图片数量与事项数量解耦。
- 每份证据只能归属一个事项或待分配区。
- 合并、拆分、释放、重新分配不会丢失或复制证据。
- 字段来源、缺项、事项提示和请求计划快照能够保存和恢复。
- 记录类型未确认时禁止正式执行。
- 多事项执行使用单一事务边界。
- 已执行会话可以开启下一轮整理而不影响已有工作记录。
